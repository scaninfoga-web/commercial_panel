PROJECT ARCHITECTURE AND DEVELOPMENT GUIDE
=========================================

Project Name: Scaninfoga Commercial Portal
Location: D:\commercial_panel\com-panel
Framework: Next.js 16 (App Router)
Language: TypeScript
UI: React 19
Styling: Tailwind CSS
State: Redux Toolkit + redux-persist
Auth: cookie-based session + middleware route protection
Backend contract: API calls via axios and custom encrypted/decrypted envelope logic


1. PROJECT PURPOSE
------------------
This project is a commercial operations portal for secure workflow management, user oversight, transaction handling, approval flows, API pricing, monitoring, and admin-like operational control.

The system is designed to behave like a controlled internal business portal, not a public-facing app. It expects secure authenticated access, restricted to allowed user tiers, and role-aware route protection.

The current implementation is a strong foundation for a production-ready internal portal, but it is still a shell that expects real backend APIs and final business workflows to be connected.


2. HIGH-LEVEL ARCHITECTURE
--------------------------
The app follows a modular Next.js App Router architecture.

Top-level layers:
- app/ : route pages, layout, root providers, route-level entry points
- components/ : UI blocks and feature modules
- lib/ : common utilities, API wrappers, auth helpers, route permissions, constants
- redux/ : global store, persisted slices, client-side session state
- actions/ : server actions or business actions
- public/ : static assets
- utils/ : helper functions and constants
- types/ : shared types
- middleware.ts : server-side route protection for protected routes

Core execution flow:
1. User loads app root route
2. Root app checks access token cookie
3. If token exists, app redirects to dashboard
4. If not, user lands on auth page
5. User login via email + MPIN + OTP flow
6. Session token + user payload saved in cookies
7. Middleware validates access for protected routes
8. UI pages consume Redux state and call backend APIs with Authorization header

6. AUTHENTICATION ARCHITECTURE
-----------------------------
Authentication is cookie-based and role-aware.

Stored values:
- accessToken
- user
- expiresAt

The user payload is stored in Redux and persisted to cookies using redux-persist and cookies-next.

Primary auth documents:
- redux/userSlice.ts
- components/pages/auth/Login.tsx
- middleware.ts
- lib/routePermissions.ts
- lib/api.ts

Auth process:
1. User enters email and MPIN
2. Client calls /api/v1/auth/signin
3. If OTP required, client requests OTP and then verifies it via /api/v1/auth/signin/verify-otp
4. On success, it saves session cookies using setCredentials
5. App redirects to /dashboard or /users depending on routing pattern
6. Middleware runs on each request and checks access token
7. Middleware also checks user tier if it is available
8. Disallowed users are redirected to /unauthorized or /auth

Important design note:
- This project was built with an internal portal security model, so the backend role/tier is considered the source of truth.
- The frontend should never trust user role information without normalizing and validating it.
- Route access logic must remain centralized in lib/routePermissions.ts and middleware.ts.


7. ROLE ACCESS MODEL
--------------------
The project defines a commercial portal access model where only allowed tiers can access the internal panel.

Allowed user tiers:
- ADMIN
- COMMERCIAL

Blocked or restricted tiers:
- NORMAL
- COOPERATIVE
- COOPERATIVE_MEMBER

Route permissions are centralized in lib/routePermissions.ts.

This is a scalable pattern because:
- one file defines the allowed tiers
- one file defines route access matrix
- middleware enforces it consistently for all pages
- login logic can reject blocked accounts before session creation

Recommended production rule:
- never hardcode role checks in each page
- always use a shared permission function or routeAccess mapping


8. STATE MANAGEMENT
-------------------
Redux is the global state layer.

Structured slices:
- userSlice.ts : authentication user data, token, expiry
- infoSlice.ts : general app information
- walletSlice.ts : wallet status and finance-related state
- store.ts : root reducer registration
- persistConfig.ts : persistence configuration for Redux slices

Why this works:
- session state is preserved across reloads
- user data is accessible globally
- auth state is centralized

Important rule:
- keep global state minimal and serializable
- do not store large derived data or heavy response blobs in Redux unless necessary
- use server fetch patterns for complex data-heavy use cases


9. API LAYER
------------
The API layer is centralized in lib/api.ts.

Responsibilities:
- build base URL
- attach Authorization bearer token when present
- attach client info headers
- attach encryption headers
- decrypt encrypted API responses automatically
- handle 401 logout by redirecting to /auth

This is a production-quality pattern because it centralizes all network concerns.

Important rules:
- never call axios directly from component files unless absolutely necessary
- use lib/api.ts as the single integration boundary for back-end calls
- centralize headers, auth, and response standards in one place

12. CODE QUALITY AND SCALABILITY RULES
--------------------------------------
These are the rules a senior developer would enforce in this project.

A. Keep business logic out of UI files
- UI components should render data and delegate logic to hooks or action functions.
- do not write backend-fetch logic directly into page components if it can be abstracted.

B. Use central auth rules
- never duplicate role checks across screens
- route permissions must be centralized
- role parsing must happen in a shared helper

C. Keep API boundaries clean
- all API calls go via lib/api.ts
- do not call axios in route files, pages, or components directly

D. Prefer shared component composition
- build from components/ui and custom reusable blocks
- avoid copying identical element patterns across features

E. Keep route protection at middleware level
- do not rely solely on UI hiding buttons to enforce security
- security must be enforced in the server/middleware layer

F. Keep session and token logic in one place
- use redux/userSlice.ts and lib/api.ts as the central source of truth

G. Normalize backend payloads before using them
- backend contracts vary across APIs
- normalize tier and role fields before using them in UI logic

H. Use typed data models
- do not use any for real business objects
- prefer explicit interfaces and shared types from types/ or lib/types.ts if needed

I. Keep route groups meaningful
- app/(sidebar)/ should contain all secure operations
- public pages should remain outside the protected shell

J. Protect against stale cookies
- always remove session cookies on logout or 401
- keep expiry aligned with backend expiry values


13. SECURITY RULES
------------------
This project must follow a few production-grade security principles:

- Only authenticated users can access the internal app shell
- Authorized user tiers must be checked in middleware
- A token must always be present before protected requests are allowed
- 401 responses should trigger logout and redirect to /auth
- Do not rely on frontend hiding elements as the only layer of security
- Any admin-like or sensitive areas must enforce server-side permission checks
- Cookie data should be minimal; do not store unnecessary secrets in client cookies
- If backend sends tier information, normalize and validate it before trusting it

16. HOW TO ADD A NEW MODULE SAFELY
----------------------------------
Use this process:

1. Define route in app/ or app/(sidebar)/
2. Create page component in components/pages/<feature>/
3. Build reusable subcomponents in components/custom or components/ui as needed
4. Use lib/api.ts for backend integration
5. Add any permission or route access in lib/routePermissions.ts
6. Add Redux slice only if global state is truly required
7. Validate all access rules through middleware and login guard
8. Run type-check and lint before completion
